[1] Router auto-reject for ray requests
- What: when a flit for mailbox 32/33 (ray request) reaches a full mailbox, the router pops it and queues a REJECT (7 << 24) to the requester's mailbox 16 + ctx, decoded from the request word (node_id << 17 | r15). Rejects use a dedicated 4-deep reject_send queue that drains before normal thread sends. An auto_rejects counter is exported to sim_logs/auto_rejects.npy and printed at the end.
- Why: a full request mailbox used to stall the low-priority NoC lane, which could back up into senders blocked in sendflit and deadlock the mesh. Now requests always drain at their destination.
- Where: core.rs constants (~L33-38), Core fields/init (~L1001, ~L1081), get_log (~L1132), cycle_output_send + new cycle_reject_send (~L1250-1300), cycle_inbound local delivery (~L1340-1375); main.rs CoreLog (~L303) and dump_logs_for_viz (~L476, ~L530, ~L570).

[11] DESIGN FIX: global ray depth was off by one at every handoff

[27] Revert [13]: restore the leaf's climb through the cached branch treelet; the receiver half resumes ABOVE its treelet
- What: removed the leaf hand-back block from [13], so the leaf again backtracks through the cached branch treelet, forwards to sibling leaves directly, and calls SEND_RAY_UP only after it finishes the branch root X (parent == null). In the branch, RESOLVE_START_NODE's returning-ray case (word 40 bit 31) now resumes at ROOT_NODE_ADDRESS->parent (goes to COMPLETE_RAY if there is none) instead of searching for a stub. That replaces the stub search from [20].
- Why: per Alex, the design is a DAG. A leaf holds every node below its parent branch root down to the sibling leaf stubs, rays only move forward in DFS order (branch even half -> leaf -> next leaf -> branch receiver half -> upward), and a ray reaching the receiver half has already traversed everything below that branch. [13] made the receiver half resume at the stub inside its treelet and forward back down, creating a branch-odd -> leaf -> branch-odd cycle (deadlock risk with bounded queues) and one round trip per leaf. Run 11 (with [13]) was at 530K cycles with only 1 traversal done. After the leaf finishes X, depth = depth(X) - 1 with X marked at that level, i.e. the state at X's parent, which is where the branch resumes.
- Still in effect from the earlier work: depth fix [11] (aligns the levels of the climb); [14] (SEND_RAY_UP with an unknown owner spills to X's queue = branch receiver queue, instead of sending to core 0xFFFF); leaf intake marks word 40 with bit 31.
- Where: leaf_core_code.s "both visited" path (block removed); branch_core_code.s RESOLVE_START_NODE / RESUME_ABOVE_TREELET.
- Open: [22] (send-loop acceptors always reject) changes the original design. Rejected rays spill to the same destination's DRAM queue, so the flow should still be forward-only, but this needs Alex's confirmation.

[28] Decision: keep [22] (send-loop acceptors always reject), checked against the DAG
- Why it's safe: a REJECT makes the requester spill the ray into the DRAM queue of the same destination it was already forwarding to, so the ray-flow graph gains no new edges and stays forward-only in DFS order. A context waiting in its send loop always gets an answer: from the receiver's EAT_RAY_INTERRUPT (another context), from the receiver's own send loop (immediate reject), or from the router auto-reject [1] when the request mailbox is full. So no context waits on another context's send loop, and the mailbox wait-for graph has no cycles. The bounded DRAM queues (spin in ENSURE_SPACE_IN_QUEUE) follow the ray-flow DAG, so a chain of full queues always ends at a sink that drains.
- Cost: rays offered to a core whose contexts are mostly sending take the slower DRAM path instead of being accepted directly.

[66] Queue reader lock: test-and-test-and-set (both firmwares). ROOT CAUSE of the cloning freezes (runs 36, 36b).
- Why: readers (producers choosing an owner) did lock += 1 and, if a writer held it (old < 0), lock -= 1 and retried immediately. A writer waits for the lock to read exactly -8192 (no readers). [113] NoC-clone handshake moved onto the protocol convention (Alex: "Build it now")
  Requests on interrupt pipes (lane 1), all responses on the per-context response mailboxes 16-31 (lane 0), router auto-NACK for a full request pipe.
  - REQUEST: unchanged, clone ctx 0 -> source pipe 34, (clone id << 17) | node key. It is now the ONLY word that uses pipe 34.
  - OFFER/REFUSE/BUSY -> clone's mailbox 16 (clones ask from context 0 during boot; no spare bits for a ctx in the request word).

[131] (Alex) Three bandwidth caps per stack, each a k-bytes-per-n-cycles window (n = DRAEM_BW_WINDOW, k = GB/s / GHz * n):
  stack<->DRAM: the [128] cap on fills/writebacks (DRAEM_BW_GBS).
  stack<->its own cores (DRAEM_CORE_LINK_GBS, default 512 GB/s per direction): local requests into the cache, local replies back out.
  stack<->other stacks (DRAEM_STACK_LINK_GBS, default 256 GB/s per direction): outgoing = far requests issued by this stack's cores + replies sent to other stacks; incoming = far requests arriving + replies arriving for this stack's cores. A far message uses the sender's outgoing and the receiver's incoming window, plus the far latency in between.
  Message sizes: request 8 B (address, op, core/register tag) + 4 B data for stores/atomics; reply 8 B. 0 GB/s disables a cap. The 512 / 256 GB/s defaults are placeholders, not from a source.
  Far requests get their departure time when issued (in issue order on the outgoing window; values are still computed at the target as before); everything else waits in a queue whose head goes when its window has room. A far reply arriving at the origin goes straight to the core (it does not also use the core link).
  core.rs: mem.submit -> mem.submit_local; far requests carry issue_cycle = mem.depart_far(...). main.rs: far requests -> mem.submit_far; replies from other stacks go into mem.far_reply_in before the model ticks. MEMSTAT adds per-link GB/s, cycles held, and queue lengths. Unit tests: windows never exceed k and saturate under overload; far miss round trip = local miss + 2 x far latency.
  Run 100 (hbm3, [130]) stopped at ~400K, still in the modeled boot (stack 0 at 16 requests/cycle, ~6.4M of ~22M boot reads done); with [130] misses on stacks 1-7 dropped from ~4,000 to ~150 cycles. Run 101 = [131], hbm3 defaults, 5M.

[160] ROOT CAUSE of the stray-word crashes (B4 7.06M, B6 7.08M, B7 1.56M) found, and the simulator made deterministic (Alex). Not a firmware bug: a race in the cross-thread NoC links. cycle_inbound peeked the incoming link (lane 0 empty -> lane 1 head, e.g. a request to this core -> 'deliver locally'), then the neighbouring stack's thread pushed a lane-0 flit into the same link, and pop_inbound (strict priority, lane 0 first) popped THAT flit and delivered it locally into its own mailbox number. Evidence: B7 [158] sender dump at 1,521,363: core 7897 ctx 0 held a valid ACK from core 7978 ctx 7 (5 words left), r10 = 0x7CA87 = 7978<<6|7 exactly, normal RAY_SEND_LOOP history, yet the word arrived at core 7999 (63,62), a stack-edge core on the path to 7978 (42,62); B7 then crashed at 1,563,609 when 7999 ctx 7 found it. Every stray receiver so far sits on a stack edge (x = 31, 63 or 95): B4 5151, B6 7327 and 3647, B7 7999, B8 5439 and 2783. The intended receiver is one word short, its EAT_RAY misaligns, and a later send loop stores the leftover to r4 = -1. Fix (core.rs): PrioritizedFlitEater::peek_ready / pop_ready choose the lane whose head is ready this cycle (lane 0 first) and pop exactly that flit; a flit pushed by another thread this cycle is never ready (latency >= 1), so the choice no longer depends on thread timing. Determinism (Alex: no run-to-run variance): (1) link admission uses start-of-cycle occupancy (Inner::pop_mark counts the consumer's pops in the current cycle), and NOC_FIFO_SIZE 1 -> 2 so a link still carries one flit per cycle with the one-cycle credit delay; (2) main.rs collects far DRAM requests and far replies from other stacks and applies only those sent in an earlier cycle, sorted by (send cycle, source stack) with each source's order kept (LongDramOp gained sent_cycle / src_stack); (3) DRAEM_STATE_HASH=N prints 'STATEHASH cycle C stack S hash' every N cycles (pcs, registers, ready bits, membits, SRAM, mailbox fills, memory stats) to compare runs.
